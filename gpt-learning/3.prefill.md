你可以先记住一句话：

**prefill 就是：模型在正式逐字生成之前，先把用户输入的 prompt 整体读一遍，并把每一层 attention 里算出来的 K、V 存进 KV Cache。**

它相当于：

```text
用户问题 / prompt
    ↓
一次性送进模型
    ↓
模型理解上下文
    ↓
把每层的 K、V 缓存起来
    ↓
开始 decode，一个 token 一个 token 生成答案
```

---

# 1. prefill 是什么？

在大模型推理时，一般分成两个阶段：

```text
1. prefill 阶段：处理输入 prompt
2. decode 阶段：逐 token 生成新内容
```

比如你输入：

```text
请解释一下 Transformer
```

模型不会一开始就直接生成答案。它要先读懂你的问题。

这个“读懂 prompt”的过程，就是 **prefill**。

更专业地说：

```text
prefill 阶段会把 prompt 中的所有 token 一次性送入 Transformer，
并计算每一层 attention 的 Q、K、V，
然后把 K、V 存进 KV Cache。
```

---

# 2. 为什么叫 prefill？

`prefill` 可以拆开理解：

```text
pre  = 之前
fill = 填充
```

也就是：

```text
在正式 decode 之前，先把 KV Cache 填好。
```

所以 prefill 的核心不是“生成很多 token”，而是：

```text
把 prompt 对应的 K、V 预先算好，并存起来。
```

例如 prompt 有 10 个 token：

```text
[t1, t2, t3, t4, t5, t6, t7, t8, t9, t10]
```

prefill 阶段会一次性处理这 10 个 token，然后在每一层存下：

```text
K_cache = [K1, K2, K3, ..., K10]
V_cache = [V1, V2, V3, ..., V10]
```

后面生成第 11 个 token 时，就不用重新计算前 10 个 token 的 K、V 了。

---

# 3. 先回顾一下 attention 里的 Q、K、V

Self-Attention 里，每个 token 会被映射成三个东西：

```text
Q：Query，我想找什么信息
K：Key，我有什么信息可以被别人匹配
V：Value，我真正提供的信息内容
```

attention 的核心计算是：

```text
Attention(Q, K, V) = softmax(QK^T / sqrt(d)) V
```

对于一个 token 来说：

```text
它用自己的 Q 去匹配所有历史 token 的 K，
得到注意力权重，
再用这些权重加权汇总对应的 V。
```

比如生成一句话：

```text
我 喜欢 机器 学习
```

当模型处理“学习”时，它可能需要看前面的：

```text
我 / 喜欢 / 机器
```

所以“学习”的 Q 会去匹配前面 token 的 K，再汇总它们的 V。

---

# 4. 没有 KV Cache 会发生什么？

假设 prompt 是：

```text
我喜欢机器学习
```

模型要继续生成：

```text
，因为它很有趣。
```

如果没有 KV Cache，生成过程会很浪费。

生成第 1 个新 token 时，输入：

```text
我喜欢机器学习
```

模型算一遍。

生成第 2 个新 token 时，输入变成：

```text
我喜欢机器学习，因为
```

模型又从头算一遍。

生成第 3 个新 token 时，输入变成：

```text
我喜欢机器学习，因为它
```

模型又从头算一遍。

问题是：前面的 prompt 每次都重复计算。

```text
我喜欢机器学习
```

这部分已经算过了，但每生成一个新 token，又重新算一遍，非常浪费。

---

# 5. 有 KV Cache 后怎么做？

有 KV Cache 后，模型会这样做：

## 第一步：prefill

一次性处理 prompt：

```text
我 / 喜欢 / 机器 / 学习
```

并把每一层的 K、V 存起来：

```text
K_cache = [K_我, K_喜欢, K_机器, K_学习]
V_cache = [V_我, V_喜欢, V_机器, V_学习]
```

## 第二步：decode

开始生成新 token。

生成“因为”时，只需要计算当前这个新 token 的 Q、K、V。

然后：

```text
当前 token 的 Q
    去看
历史 K_cache + 当前 K
```

也就是：

```text
Q_因为 attend to [K_我, K_喜欢, K_机器, K_学习, K_因为]
```

生成完“因为”后，把它自己的 K、V 也追加到 cache：

```text
K_cache = [K_我, K_喜欢, K_机器, K_学习, K_因为]
V_cache = [V_我, V_喜欢, V_机器, V_学习, V_因为]
```

然后继续生成下一个 token。

---

# 6. prefill 和 decode 的区别

可以这样对比：

```text
prefill 阶段：
一次性处理整个 prompt
输入长度 T 通常大于 1
主要目的是理解上下文，并填充 KV Cache
可以并行计算

decode 阶段：
一次只处理 1 个新 token
输入长度通常是 1
主要目的是生成下一个 token
每生成一个 token，就把它的 K、V 追加到 cache
```

用表格看更清楚：


| 阶段    | 输入                    | 是否生成新 token                  | 是否填 KV Cache | 计算方式                   |
| ------- | ----------------------- | --------------------------------- | --------------- | -------------------------- |
| prefill | 整个 prompt             | 通常只得到第一个生成位置的 logits | 会              | 并行处理多个 token         |
| decode  | 上一步生成的 1 个 token | 会                                | 会追加          | 一个 token 一个 token 处理 |

注意：prefill 阶段最后也会输出 logits，用来采样第一个生成 token。

---

# 7. 为什么 prefill 阶段还要 causal mask？

这是一个非常关键的点。

假设 prompt 是：

```text
A B C D
```

prefill 阶段会一次性把 `A B C D` 全部送进模型。

但是对于自回归语言模型来说，位置 1 不能看到位置 2、3、4。

也就是说：

```text
A 只能看 A
B 只能看 A, B
C 只能看 A, B, C
D 只能看 A, B, C, D
```

不能让：

```text
A 看到 B C D
B 看到 C D
C 看到 D
```

否则训练/推理逻辑就变成“偷看未来”。

所以 prefill 虽然是并行计算整个 prompt，但仍然必须用 causal mask。

矩阵大概是这样：

```text
      A  B  C  D
A     ✓  ✗  ✗  ✗
B     ✓  ✓  ✗  ✗
C     ✓  ✓  ✓  ✗
D     ✓  ✓  ✓  ✓
```

这就是 causal mask。

---

# 8. 为什么 decode 阶段可以不用 mask？

decode 阶段一次只输入一个新 token。

比如当前已经有 cache：

```text
A B C D
```

现在要处理新 token：

```text
E
```

此时 cache 里全是历史 token：

```text
A B C D
```

再加上当前 token：

```text
E
```

它天然只能看到：

```text
A B C D E
```

因为未来的 token 还没生成出来。

所以对于当前这个单个 token 来说，不存在“偷看未来”的问题。

因此很多实现里 decode 阶段可以不用 causal mask。

你笔记里的这句话就是这个意思：

```text
T_q == 1 && T_kv > 1：decode 阶段，不用 mask
```

因为：

```text
当前 query 只有 1 个；
KV cache 里都是过去已经生成的 token；
未来 token 还不存在。
```

# 9. T\_q 和 T\_kv 是什么意思？

你笔记里写了：

```text
T_q = T_kv = T
T_q == 1 && T_kv > 1
```

这里需要解释清楚。

在 attention 里：

```text
Q 的序列长度叫 T_q
K/V 的序列长度叫 T_kv
```

也就是：

```text
Q: 当前要查询的位置
K/V: 可以被查询的上下文位置
```

---

## 正常训练或 prefill

输入一整段序列：

```text
A B C D
```

这时候：

```text
Q 来自 A B C D
K 来自 A B C D
V 来自 A B C D
```

所以：

```text
T_q = 4
T_kv = 4
```

也就是：

```text
T_q == T_kv
```

因为所有 token 都一起进来了。

但是要用 causal mask，防止前面的 token 看后面的 token。

---

## decode 阶段

假设历史 cache 里已有：

```text
A B C D
```

现在新输入一个 token：

```text
E
```

这时候：

```text
Q 只来自当前 token E
```

所以：

```text
T_q = 1
```

但是 K/V 来自：

```text
A B C D E
```

所以：

```text
T_kv = 5
```

于是：

```text
T_q == 1
T_kv > 1
```

这就是 decode 阶段。

# 10. 用形状理解 prefill

假设：

```text
batch_size = B
prompt 长度 = T
embedding 维度 = C
head 数量 = n_head
每个 head 的维度 = head_dim
```

输入 token id：

```text
idx.shape = [B, T]
```

token embedding 后：

```text
x.shape = [B, T, C]
```

进入 attention 后，得到：

```text
q.shape = [B, n_head, T, head_dim]
k.shape = [B, n_head, T, head_dim]
v.shape = [B, n_head, T, head_dim]
```

prefill 阶段会把 k、v 存进 cache：

```text
kv_cache.k.shape = [B, n_head, T, head_dim]
kv_cache.v.shape = [B, n_head, T, head_dim]
```

如果模型有 12 层 Transformer block，那么每一层都有自己的 K/V cache。

也就是说，不是一份全局 cache，而是：

```text
layer 0: K_cache, V_cache
layer 1: K_cache, V_cache
layer 2: K_cache, V_cache
...
layer 11: K_cache, V_cache
```

因为每一层的 hidden state 不一样，所以每一层算出来的 K、V 也不一样。

---

# 11. 用形状理解 decode

prefill 后，cache 里已有 prompt 的 K/V。

假设 prompt 长度是 4：

```text
K_cache.shape = [B, n_head, 4, head_dim]
V_cache.shape = [B, n_head, 4, head_dim]
```

现在 decode 一个新 token。

当前输入长度是 1：

```text
x.shape = [B, 1, C]
```

算出当前 token 的：

```text
q_new.shape = [B, n_head, 1, head_dim]
k_new.shape = [B, n_head, 1, head_dim]
v_new.shape = [B, n_head, 1, head_dim]
```

然后把新的 k/v 追加到 cache：

```text
K_cache = concat([K_cache, k_new], dim=sequence_length)
V_cache = concat([V_cache, v_new], dim=sequence_length)
```

变成：

```text
K_cache.shape = [B, n_head, 5, head_dim]
V_cache.shape = [B, n_head, 5, head_dim]
```

当前 token 的 query 会 attend to 全部 K：

```text
q_new attends to K_cache
```

也就是：

```text
当前 token 看所有历史 token + 自己
```

# 12. prefill 真的加速了吗？

这里要特别精确。

**KV Cache 最明显加速的是 decode 阶段。**

因为没有 cache 时，每生成一个 token，都要重新计算整个前缀。

有 cache 时，每次只需要计算新 token 的 Q/K/V，然后复用历史 K/V。

但是 prefill 本身也很关键，因为：

```text
prefill 阶段负责把 prompt 的 K/V 一次性算出来并填入 cache。
```

所以更准确地说：

```text
prefill 是 KV Cache 的初始化阶段；
KV Cache 主要让后续 decode 更快。
```

不能简单理解成：

```text
prefill 本身让 prompt 计算量变少
```

它的主要作用是：

```text
避免后续生成时重复计算 prompt 的 K/V。
```

---

# 13. 没有 cache 和有 cache 的生成对比

假设 prompt 长度是 100，要生成 50 个 token。

## 没有 KV Cache

生成第 1 个 token：计算长度 100

生成第 2 个 token：计算长度 101

生成第 3 个 token：计算长度 102

……

生成第 50 个 token：计算长度 149

总计算里有大量重复。

---

## 有 KV Cache

prefill 一次：计算长度 100

之后每次 decode：

```text
只计算 1 个新 token 的 Q/K/V
复用前面所有 token 的 K/V
```

生成 50 个 token，就是 50 次单 token decode。

所以流程变成：

```text
一次 prefill + 多次 decode
```

这就是大模型推理服务的经典结构。

---

# 14. 为什么 prefill 可以并行？

prefill 输入的是完整 prompt：

```text
A B C D E
```

虽然有 causal mask，但这 5 个 token 的 Q/K/V 可以一起算。

也就是说：

```text
Q_A, Q_B, Q_C, Q_D, Q_E
K_A, K_B, K_C, K_D, K_E
V_A, V_B, V_C, V_D, V_E
```

都可以通过矩阵乘法并行计算。

只是 attention 权重里通过 mask 限制：

```text
A 不看 B C D E
B 不看 C D E
C 不看 D E
...
```

所以 prefill 很适合 GPU 并行。

decode 阶段则不同，因为生成第 n 个 token 之前，你不知道第 n-1 个 token 是什么。

所以 decode 是强自回归的：

```text
生成 token 1
再生成 token 2
再生成 token 3
```

不能完全并行。

# 15. prefill 的完整算法流程

假设输入 prompt：

```text
prompt = "猫吃鱼"
```

经过 tokenizer：

```text
input_ids = [猫, 吃, 鱼]
```

## prefill 阶段

```python
# input_ids shape: [B, T]
x = tok_emb(input_ids) + pos_emb[:T]

for layer in transformer_layers:
    q, k, v = layer.attn.project_qkv(x)

    # prefill 阶段：T_q = T_kv = T
    # 使用 causal mask
    attn_out = causal_attention(q, k, v, mask=True)

    # 把这一层的 K/V 存入 cache
    kv_cache[layer].k = k
    kv_cache[layer].v = v

    x = layer.output(attn_out)

logits = lm_head(x)
next_token_logits = logits[:, -1, :]
```

最后拿最后一个位置的 logits 去采样第一个生成 token：

```text
比如生成：“了”
```

---

## decode 阶段

现在输入只有刚刚生成的 token：

```text
input_ids = [了]
```

```python
x = tok_emb(input_ids) + pos_emb[current_position]

for layer in transformer_layers:
    q_new, k_new, v_new = layer.attn.project_qkv(x)

    # 追加到历史 cache
    k_all = concat(k_cache[layer].k, k_new)
    v_all = concat(k_cache[layer].v, v_new)

    # decode 阶段：T_q = 1, T_kv > 1
    # 通常不用 causal mask
    attn_out = attention(q_new, k_all, v_all, mask=False)

    # 更新 cache
    kv_cache[layer].k = k_all
    kv_cache[layer].v = v_all

    x = layer.output(attn_out)

logits = lm_head(x)
next_token = sample(logits[:, -1, :])
```

然后继续循环。

# 16. 结合你的接口理解

你给的逻辑是：

```text
kv_cache is None：
正常训练，T_q = T_kv = T，用 causal mask

kv_cache 不为 None：
  T_q == T_kv：prefill 阶段，把 K、V 追加到 cache，仍然用 causal mask
  T_q == 1 && T_kv > 1：decode 阶段，把 K、V 追加到 cache，不用 mask
```

可以这样理解：

---

## 情况一：kv\_cache is None

这是普通训练或者不使用 cache 的 forward。

输入：

```text
[B, T]
```

Q/K/V 都来自这段输入。

```text
T_q = T_kv = T
```

必须用 causal mask。

---

## 情况二：kv\_cache 不为 None，且 T\_q == T\_kv

这是 prefill。

说明你传入了一整段 prompt。

例如：

```text
prompt = [A, B, C, D]
```

这时候：

```text
Q = [Q_A, Q_B, Q_C, Q_D]
K = [K_A, K_B, K_C, K_D]
V = [V_A, V_B, V_C, V_D]
```

所以：

```text
T_q = 4
T_kv = 4
```

但因为这是自回归模型，仍然要 causal mask。

然后把 K/V 存进 cache：

```text
cache = [A, B, C, D] 的 K/V
```

---

## 情况三：kv\_cache 不为 None，且 T\_q == 1, T\_kv > 1

这是 decode。

说明当前只输入一个新 token，但 K/V 已经包含历史。

例如：

```text
历史 cache = [A, B, C, D]
当前 token = E
```

当前 query 只有：

```text
Q_E
```

所以：

```text
T_q = 1
```

但是 K/V 是：

```text
K_A, K_B, K_C, K_D, K_E
V_A, V_B, V_C, V_D, V_E
```

所以：

```text
T_kv = 5
```

这里不用 mask，因为未来 token 根本不存在。

# 18. 为什么 KV Cache 存 K/V，不存 Q？

这是一个非常好的理解点。

生成下一个 token 时，当前 token 需要用自己的 Q 去查历史信息。

历史 token 的 K/V 会反复被后面的 token 使用。

比如：

```text
A B C D E F
```

当生成 E 时，要用到 A-D 的 K/V。

当生成 F 时，还要用到 A-E 的 K/V。

所以历史 K/V 很有复用价值。

但是历史 Q 通常不需要复用。

因为：

```text
Q 是“当前 token 主动查询别人”的向量。
```

生成新 token 时，只需要当前 token 的 Q。

历史 token 的 Q 是它们当时查询别人用的，对当前 token 查询历史没有直接用。

所以 cache 主要存：

```text
K_cache
V_cache
```

不存：

```text
Q_cache
```

# 19. prefill 在大模型服务中的意义

在线推理服务里，一个请求通常分为：

```text
prefill latency
decode latency
```

prefill latency 是：

```text
处理 prompt 所花的时间
```

decode latency 是：

```text
逐 token 生成答案所花的时间
```

比如用户输入很长：

```text
请阅读下面 10 万字文档，并总结核心观点
```

那么 prefill 会很重，因为模型要先把这 10 万字对应的 token 全部处理一遍。

如果用户输入很短，但要求输出很长，那么 decode 会更重。

所以：

```text
长输入任务：prefill 压力大
长输出任务：decode 压力大
```

例如：

```text
RAG 长文档问答：prefill 很重
写一篇长文章：decode 很重
聊天短问短答：prefill 和 decode 都较轻
```

# 20. 最后总结

你可以这样记：

```text
prefill = 先读题
decode = 开始作答
KV Cache = 草稿纸上已经记好的上下文信息
```

更专业地说：

```text
prefill 阶段：
把 prompt 中所有 token 并行送进模型；
计算每层 attention 的 K/V；
使用 causal mask；
把 K/V 写入 KV Cache；
输出最后一个位置的 logits，用来生成第一个新 token。
```

```text
decode 阶段：
每次只输入一个新 token；
只计算当前 token 的 Q/K/V；
把当前 K/V 追加到 cache；
当前 Q attend to 历史 K/V；
通常不用 causal mask；
不断生成下一个 token。
```

最关键的一句话：

```text
prefill 负责把 prompt 的上下文“预填充”进 KV Cache；
decode 负责利用这个 cache 高效地逐 token 生成。
```

所以你笔记里的这段可以理解成：

```text
kv_cache is None：
普通训练或普通 forward，不做缓存。

kv_cache 不为空，T_q == T_kv：
prefill，整段 prompt 进入模型，K/V 写入 cache，需要 causal mask。

kv_cache 不为空，T_q == 1 且 T_kv > 1：
decode，只处理当前新 token，复用历史 K/V，一般不需要 mask。
```
